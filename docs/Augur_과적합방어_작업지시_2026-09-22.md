# 작업 A — 상수 민감도 스윕

## 목적

헤드라인 두 숫자가 **우리가 고른 상수**에 얼마나 의존하는지 측정한다.
심사자가 "그 숫자는 당신들 설정의 함수 아닌가"라고 물을 때 표로 답하기 위한 것이다.

## 대상 숫자

| | 양 | 현재 값 | 출처 |
|---|---|---|---|
| A1 | 총 불확도 / 핏 전파 σ | **1.72–2.68배** (분모 0.0501 ppb, 정렬 기준 n=8,847) | `augur_AMT_§4_초고.md` §4.4 |
| A2 | 종료상태 분해 | **34.3 %** = STEP_LIMITED 21.4 % + AT_BOUND 12.8 % (8,446 스캔) | §5.2 |

## 축 — OAT(one-at-a-time), 완전 격자 아님

기준 설정에서 **한 번에 하나씩만** 바꾼다. 완전 격자는 36조합이라 비용이 맞지 않는다.

| 축 | 값 | 비기준 변형 수 | 비고 |
|---|---|---|---|
| shift 탐색 상자 | 반폭 0.5× / **1.0×(기준)** / 2.0× | 2 | **아래 A-0 참조 — ±6 대칭 상자가 아니다** |
| 스텝 리밋 | **on(기준)** / off | 1 | **A2에 가장 큰 영향이 예상됨** |
| 시드 개수 | 5 / **13(기준)** | 1 | |
| 다항 차수 | poly−1 / **poly(기준)** / poly+1 | 2 | 채널별 운영 차수 기준 |

→ 기준 1개 + 변형 (2+1+1+2) = **7 조합**

### A-0. shift 상자 축의 정의 — 운영 중심 유지, 반폭만 배율

초안의 `±4/±6/±8 px`는 **틀렸다.** 운영 fitset(2026-09-17)에 ±6 대칭 상자를 쓰는 채널은 없고, ch1은 애초에 비대칭이다.

| 채널 | 운영 `sh_val` | 중심 | 반폭 |
|---|---|---|---|
| ch1 (ANs) | `-10, 0.5` | **−4.75** | **5.25** |
| ch2 (PNs) | `-5, 5` | 0 | 5 |
| cold | `-1, 1` | 0 | 1 |

**정의: 채널별 운영 중심을 고정하고 반폭에만 배율을 건다.**

```
lo = center - halfwidth * scale
hi = center + halfwidth * scale
scale ∈ {0.5, 1.0(기준), 2.0}
```

가산(±2 px 등)이 아니라 **배율**을 쓰는 이유: 반폭이 채널 간 5배 차이 나므로(5.25 / 5 / 1) 가산은 ch1에는 무의미하고 cold에는 과도하다.

**중심을 옮기지 않는 이유**: 중심은 그 채널의 실제 파장 정렬 기대값을 담고 있다. ch1의 비대칭은 오류가 아니라 정보이므로 **비대칭을 보존한 채로** 배율을 건다.

산출되는 상자 (실행 전 코드에서 운영값을 다시 읽어 확인할 것):

| 채널 | 0.5× | 1.0×(기준) | 2.0× |
|---|---|---|---|
| ch1 ANs | −7.375 … −2.125 | −10 … 0.5 | −15.25 … 5.75 |
| ch2 PNs | −2.5 … 2.5 | −5 … 5 | −10 … 10 |
| cold | −0.5 … 0.5 | −1 … 1 | −2 … 2 |

### A-0b. 먼저 재야 할 것 — 현재 shift가 상자 안 어디에 있는가

스윕 결과를 해석하려면 **기준 상태에서 적합된 shift의 분포가 상자 경계로부터 얼마나 떨어져 있는지**를 먼저 알아야 한다. 조합을 늘리지 않는 사전 측정이다.

채널별로 산출: 적합 shift의 5/25/50/75/95 분위수, 하한 적중률, 상한 적중률.

> 기록상 cold는 운영에서 **22/22가 정확히 −1.000**, 즉 전량 하한 고착이다. 이것이 재현되는지 먼저 확인할 것. 재현되지 않으면 거기서 멈추고 보고한다.

**해석 시 주의 (보고서에 명시할 것)**: 0.5× 상자는 **대안 설정이 아니라 스트레스 테스트**다. 현재 적합 shift가 상자 가장자리에 몰려 있는 채널에서는 0.5×가 그 값들을 상자 밖으로 밀어내므로 전량 경계 고착이 나오는 것이 정상이다. 이를 "0.5×가 더 나쁘다"로 읽지 말 것.

## 비용 설계 — 이게 중요하다

- **A2(종료상태)**: 조합당 8,446 스캔 1패스. 싸다. **7 조합 전부 돌린다.**

# 작업 B — 벤치마크 계기 파라미터 공간 확장

## ⚠️ 선결 조건 두 가지 — 확인 완료

### B-0-1. 생성기가 저장소에 없다

`generate.py`는 저장소 어디에도 없고 **배포 zip 안에만** 있다.
→ 먼저 벤치마크 패키지를 `benchmark/doas_benchmark_v1/`로 풀어 커밋할 것. 그래야 버전 관리가 된다.

### B-0-2. 🔴 H2O 단면에 convolve 전 원본이 없다 — **사용자 결정 대기**

ILS를 바꾸려면 **convolve 전 고해상 단면**에서 다시 convolve해야 한다. 이미 convolve된 단면을 다시 넓히는 것은 (정확히는) 불가능하다.

저장소 `reference_data/raw/` 현황:

| 기체 | 원본 | ILS 변형 가능? |
|---|---|---|
| NO₂ | `NO2_Vandaele(2002)_294K_384-725nm(vis-dilut5).txt` (9.3 MB) | ✅ |
| CHOCHO | `CHOCHO_Volkamer(2005)_296K_250.031-526.168nm(0.001nm).txt` (5.2 MB) | ✅ |
| O₄ | `O4_ThalmanVolkamer(2013)_293K_335.749-600.802nm.txt` | ✅ (현재 벤치마크에는 없음) |
| **H₂O** | **`Ref_H2O-HITRAN_Dynamic-ILS-Applied.dat` 뿐 — 이미 ILS 적용됨** | ❌ |

### ✅ 결정됨 (2026-09-22, 사용자): **선택지 B — HITRAN 라인리스트를 새로 받아 직접 convolve**

(기각된 대안: A = ILS 변형 케이스에서 H₂O 제외 / C = H₂O만 현재 convolution 고정(물리적 부정합))

**A 작업은 이 결정과 무관하게 먼저 진행한다.** B-1 이후에나 쓰인다.

### B-0-3. 🔴 결정에 따라오는 선결 조건 — ILS 모델부터 확정할 것

현재 레퍼런스 파일명이 **`Dynamic-ILS-Applied`**다. 즉 적용된 ILS가 **파장에 따라 변하는 함수**일 가능성이 높다. 그렇다면 "ILS 0.5×"는 단일 FWHM에 배율을 거는 것이 아니라 **그 함수 전체에 배율을 거는 것**이다.

이것은 H₂O만의 문제가 아니라 **NO₂·CHOCHO에도 똑같이 걸린다.** 재-convolve 파이프라인이 기존 파일을 만든 ILS 모델을 재현하지 못하면, ILS 변형 케이스 전체가 기준 케이스와 정합하지 않는다.

**순서:**

1. 기존 `Ref_*_Dynamic-ILS-Applied.dat`를 만든 **ILS 모델을 코드에서 식별**한다 (상수 FWHM인가, 파장 의존 함수인가, 어떤 커널 형태인가, 어디에 정의돼 있는가). 저장소 안에 생성 코드가 있으면 그것이 정본이다.
2. **재현 게이트 (하드 요구사항).** 새 convolve 파이프라인을 `--ils-scale 1.0`으로 돌렸을 때, **NO₂·CHOCHO·H₂O 세 기체 모두** 기존 `Ref_*_Dynamic-ILS-Applied.dat`를 재현해야 한다. 허용 오차를 정하고 실제 편차를 보고할 것.
3. **재현에 실패하면 거기서 멈추고 보고한다.** 임의로 맞추려 하지 말 것 — 원인이 라인리스트 버전, T/P 설정, ILS 모델 중 무엇인지가 그 자체로 필요한 정보다.
4. 게이트를 통과한 뒤에만 ILS 배율 축을 돌린다.

**대체 경로**: 게이트를 통과하지 못하고 원인도 규명되지 않으면, **선택지 A(ILS 변형 케이스에서 H₂O 제외)로 후퇴**하고 그 사실을 벤치마크 README에 명시한다. 이 후퇴는 사용자 승인 후에만.

### B-0-4. HITRAN H₂O 산출 절차

- 창: 438–476 nm ≈ **21,000–22,830 cm⁻¹**
- 도구: **HAPI** (HITRAN Application Programming Interface, Python). `hitran.org`에서 라인 파라미터를 받아 `absorptionCoefficient_Voigt`로 단면을 계산한다. 로컬 실행이므로 네트워크 제약은 없을 것이다.
- **T·P를 반드시 명시할 것.** 기존 레퍼런스가 어느 T·P로 만들어졌는지 먼저 확인하고 같은 값을 쓴다. 다르면 재현 게이트가 통과하지 못한다.
- 받은 라인리스트와 HITRAN 버전을 `reference_data/raw/`에 원본 그대로 보관하고 출처를 기록한다 (Copernicus **Code and data availability** 절에 필요).

> ⚠️ **물리적 주의**: 438–476 nm의 H₂O는 고차 배진동대라 흡수가 매우 약하다. 계산된 단면의 크기가 기존 파일과 자릿수부터 다르면, 단위 변환이나 라인 선택이 잘못됐을 가능성을 먼저 의심할 것.
