## 3. 시각 디코딩 — `bytepack = (col0<<16)|col1`

### 3.1 바이트 순서의 직접 증거 (실데이터)

`2026-05-17-001.dat` row 275→276에서 **32비트 빌림(borrow)이 그대로 보인다**:

```
row 275  c0=17977  c1=5455..5648
row 276  c0=17976  c1=65261        <- c1이 0을 넘어 뒤로 감기고 c0이 1 줄어듦
```

`c1`이 아래로 래핑할 때 `c0`이 정확히 1 감소한다 = **c0이 상위 16비트**.
이름(`time_lo`/`COL_TIME_LO`)이 반대로 붙어 있는 것은 문서에 적힌 대로 역사적
오명이며, **수식이 정본**임이 실데이터로 확정된다. 순서를 뒤집으면 안 된다.

- **파일명 날짜 vs 디코드 날짜: 2065/2065 일치, 불일치 0건.**

## 4. 발견 — 조치한 것 / 결정이 필요한 것

### 4-A. [수정함] 헤더행이 데이터행보다 **넓으면** 데이터행이 전부 버려졌다

`raw_parser._detect_layout`은 등록 레이아웃(6179/6181)과 맞는 행이 하나도 없으면
**첫 행**의 열수를 썼다. 콜드 6174 파일은 헤더 6177 > 데이터 6174라 `layout.ncols=6177`이
되고, `iter_rows`의 `len(toks) < ncols` 가드가 **데이터행을 전부 버렸다.**

실측: `2026-06-11-020.dat` → `iter_rows()`가 **3694행 중 1행**(그 헤더행)만 냈다.
`kind=unknown(2ch structural)`, `hk_map={}`.

2026-09-14의 `LAYOUT_PROBE_ROWS` 수정은 "여러 행을 훑는다"까지는 갔지만
**"등록 레이아웃과 맞는 행"만 받아들이고 나머지는 첫 행으로 폴백**해서, 헤더가
**넓은** 방향은 그대로 남아 있었다. (핫은 헤더가 **좁아서** 증상이 안 났다.)

**수정**: 등록 레이아웃과 맞는 행이 없으면 훑은 행들의 **최빈 열수**를 쓴다
(동률이면 좁은 쪽 — 넓게 잡아야만 행을 버리므로).
→ `2026-06-11-020.dat`: 1행 → **3694행**. 등록 구성(6179/6181) 판정은 불변.

**기존 산출물 영향 없음**: `RawParser` 클래스 소비자는 `gui/ui_peak_trend.py`,
`tools/check_timestamps.py`, `tools/plot_spectra_by_date.py` 뿐이다(진단·시각화).
알파/R/피팅 본 파이프라인은 `core/data_io.py`를 탄다.

**회귀검사**: `tools/test_raw_layout.py` `[2-C]` — 수정 전엔 `ncols=6177`·`rows=1`로
FAIL(실파일 증상과 동일), 수정 후 PASS.

### 4-J. raw 포맷은 **3채널 전제**다 — 세 번째 슬롯에 아무도 접근 못 한다

**계기 담당자 확인(2026-09-15)**: 이 raw 포맷은 애초에 채널 **3개**를 가정하고 짠
LabVIEW 코드다(2개도 1개도 아니다). 이게 레이아웃 전체를 설명한다:

```
meta          0 - 4      (5열)
슬롯 A      5 - 2052     (2048px)   MATLAB 이름 ch3   2026: 미사용(노이즈)
슬롯 B   2053 - 4100     (2048px)   MATLAB 이름 ch1   2026: Cold NO2 / Hot PNs
슬롯 C   4101 - 6148     (2048px)   MATLAB 이름 ch2   2026: Hot ANs (Cold는 노이즈)
HK         6149 -                   장비마다 열 수가 다름
```

즉 **스펙트럼 구간은 언제나 6149열로 고정**이고(5 + 3×2048), 그 뒤 HK 열 수만
장비·구성에 따라 달라진다. 그래서:

    ncols − 6149 = HK 열 개수
    핫 6181 → HK 32 · 콜드 6179 → HK 30 · 콜드(선두결손) 6174 → HK 25

"콜드와 핫은 raw 포맷이 다르다"가 아니라 **"포맷은 같고 HK 개수만 다르다"**가 맞는
설명이다. §1.1 의 열수 분포도 이 틀로 보면 전부 자연스럽다.

MATLAB 채널 번호는 슬롯 순서와 다르다(`ch3` 가 파일 맨 앞). 이건
`tools/validate_pipeline.py` 의 `c_raw` 가 `{"ch1":(2053,4101), "ch2":(4101,6149),
"ch3":(5,2053)}` 로 **바이트 일치**를 통과하며 확정한 사실이다 — 추측이 아니다.

#### 그런데 세 번째 슬롯(5–2052)은 두 모듈 다 접근하지 못한다

| | 블록을 어디서부터 세나 | 결과 |
|---|---|---|
| `data_io._load_file_to_cache` | **5** 부터 (`nblk = (ncol-5)//2048`) | 3슬롯 — 파싱은 함 |
| `data_io.load_measurement_with_hk` | **2053** 부터 (`META_COLS + (ch-1)*2048`) | 2슬롯 — **주소가 없음** |
| `raw_parser.spec_blocks_for_ncols` | **2053** 부터 | 2슬롯 — 슬롯 A 를 못 봄 |
| `raw_parser._detect_n_channels_from_row` | **2053** 부터 | 2슬롯 |

같은 파일을 한쪽은 3블록, 다른 쪽은 2블록으로 센다. 그리고 **`channel=3` 을
요청하면 조용히 `channel=2` 로 clamp 돼 ch2 데이터가 돌아온다**(실측:
2026-05-18-001 에서 channel=2 와 channel=3 의 max 가 44241 로 동일) — 경고 없음.

**다음 캠페인에서 세 번째 캐비티를 켜면 조용히 사라진다**: 슬롯이 이미 자리를
차지하고 있으므로 **ncols 는 그대로 6181/6179** 이고, 레지스트리는 여전히
채널 2개만 적혀 있으며, `channel=3` 은 clamp 된다. 열 수가 안 바뀌니
"새 구성은 JSON 만 얹으면 된다"는 경로도 안 열린다(같은 ncols 를 덮지 않으므로).

**고칠 방향** — 어차피 `data_io` 고정열 전환(§4-B 후속)을 할 때 같이 정리한다:
1. 블록 인덱싱을 **5 기준 3슬롯**으로 통일한다(그게 포맷의 진실이다).
2. `channel` 이 범위를 넘으면 **조용히 clamp 하지 말고 예외/경고**. 지금은 잘못된
   채널을 요청해도 다른 채널 데이터가 조용히 돌아온다 — 무결성 헌장 위반에 가깝다.
3. 어느 슬롯이 어느 가스인지는 **레지스트리/프로파일이 정한다**(2026 여수는
   슬롯 B·C 만 활성). 슬롯 A 가 켜지는 구성은 그때 항목을 추가하면 된다.

### 4-K. [확정] sentinel — 이 계기는 "값 없음"을 **0** 으로 쓴다

**계기 담당자 확인(2026-09-15)**: 데이터를 오래 본 경험상 이 계기는 미연결/미측정
채널에 **0** 을 쓴다. 전수조사가 이를 뒷받침한다 — 핫 1314개 전 파일에서
`tempcell3`(6176)·`tempsptrm`(6177)이 **한 번도** 0 이 아닌 적이 없고,
`templed4`(6152)는 늘 65535 다(두 표기가 섞여 쓰인다).

→ `SENTINEL_RAW = (0.0, 65535.0)` 은 **맞다.** 바꾸지 않는다.

⚠ **대가**: 정확히 `0.00 °C`(또는 raw 0)는 **원리적으로 결측과 구분되지 않는다.**
HK 판독이 그 필드를 NaN 으로 보고 폴백한다(핫이면 셀히터 설정값 75 °C → ppb +15 %).

| 셀 온도 | 읽힘 |
|---|---|
| −40 · −5 · 5 · 30 · 120 °C | 정상 (§4-B 수정 후) |
| **0.00 °C** | **75.00 (폴백)** ← 이 한 점만 |

0.01 °C 분해능이라 셀이 딱 `0.00` 에 앉아야 걸린다. 여수(셀 29~33 °C)에서는 실제로
걸린 적이 없다. 다만 **빙점 근처 운용(한랭지·항공·야간 해양)이면 반복될 수 있다.**

**고칠 때가 오면**: 0 을 목록에서 빼면 안 된다(위의 죽은 열들이 0.00 °C 를 실측값으로
보고하게 된다). **필드별 sentinel 을 프로파일에** 두는 것이 답이다 —
`hk.fields[].sentinel: [65535]` 처럼. 그때까지는 YAGNI.
근거 주석은 `core/raw_parser.py` 의 `SENTINEL_RAW` 바로 위(단일 출처).
