## 1. 공개용 히스토리 준비 (main은 그대로 두고 별도 이력으로)

105개 커밋짜리 실제 개발 히스토리(디버깅 왕복, 실험적 시도, 내부 논의 등)를 그대로 공개하면
검토 과정 노이즈가 논문 검토와 무관하게 노출된다. **main을 rebase/force-push 하지 말고**,
그 시점의 main 스냅샷을 기준으로 새 orphan 이력을 만들어 별도 공개 저장소(또는 같은 저장소의
public 브랜치)로 전환하는 방식을 권장:

```bash
# 그 시점의 main에서 시작
git checkout main
git pull origin main

# 스냅샷을 기준으로 커밋 이력 없는 새 브랜치 생성
git checkout --orphan public-release
git add -A
git commit -m "Augur (CAESAR) vX.Y.Z — public release for AMT submission"

# (선택) 논문에 맞는 버전 태그
git tag -a vX.Y.Z -m "AMT submission release"
```

이렇게 하면 `main`(실제 개발용, private 유지 가능)과 `public-release`(공개용, 단일/소수
커밋)가 분리된다. 저장소 자체를 public으로 바꾸기 전에 `public-release` 브랜치만 먼저
새 public 저장소로 push해서 확인하는 것도 방법.

```
The Augur (CAESAR) analysis software is available at

Raw instrument data are not publicly distributed; they are available from the
```

DOI·버전 번호는 §4 완료 후 채울 것. **원자료 비공개는 §2의 확정 결정이므로, 위 문구의

교신저자 결정.
